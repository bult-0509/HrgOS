# 设备定位流程与服务器通信验收（2026-10-07）

当前不能通过公网入口跑通完整活动。最先要解决的是 `https://hrgos.skyseiun.com` 的 API 入口：首页返回 200，但 `/api/health`、正式赛局状态和隔离测试状态均返回 Nginx 的 HTML 404，而非后端 JSON。这个结果不能区分 API 服务未部署、未启动、代理遗漏或上游地址错误；需要检查实际部署。不要把网站能打开当成后端可用。

本轮没有修改线上比赛、部署配置、能力卡数值或定位业务逻辑。只增加可重复执行的本机诊断脚本与报告。测试 GPS 均为合成坐标，未采集真实设备位置。安卓和 iPhone 都列入后续验收，但本轮没有取得两台手机的实际操作结果。

## 必须先处理的问题

### 1. 公网API入口没有跑通

三个实际探测路径：

- `/api/health`：404、`text/html`、Nginx错误页。
- `/api/games/location-probe/state`：404、`text/html`、Nginx错误页。
- `/api/testing/runs/location-probe/state`：404、`text/html`、Nginx错误页。

检查顺序：API进程/容器是否运行 → 上游监听地址与端口 → Nginx/隧道的 `/api/*` 路由 → 数据库连接与持久卷 → 正式前端版本和API基址。健康检查应返回JSON、数据库类型 `postgresql`、正式接口已启用。状态路径没有会话时应返回后端JSON权限错误，而非静态站点错误页。

测试期间需要独立测试接口和测试密钥；本机没有发现已配置的远端 `HRG_TEST_API_URL` / `TEST_API_KEY` 或 `.env.test.local`。本机测试密钥不能当作远端密钥。密钥不需要粘贴到聊天或前端URL中。

### 2. 正式定位页面与已测试模块不是同一套逻辑

`src/ability/AbilityApp.tsx:90` 的正式页面直接调用 `watchPosition`。它没有接入 `createLocationReporter`：

- 进入后台仅在回调里跳过发送，没有监听 `visibilitychange` 清理GPS采集。
- 暂停、READY时仍可能建立GPS监听，只是在回调里跳过发送。
- 判定没有检查 `view.team.finishedAt`；队伍完赛但全局仍RUNNING时，仍可能发请求并得到 `TEAM_FINISHED`。
- 三秒内的GPS回调直接丢弃，没有保证窗口尾部发送最新点。
- 权限拒绝、临时不可用和超时统一关闭tracking，临时GPS错误也需要人工重新开启。
- 没有以成功上传时间显示定位健康度；GPS回调是否持续发生未有安卓/iPhone实机证据。若设备静止时回调不足20秒一次，服务端会标离线，即使网络正常。

应统一正式页面与被验证的定位生命周期，并为完赛、暂停、前后台切换、权限拒绝、临时GPS失败、网络恢复和静止设备补验。不要用定位模块的两个单元测试代表正式页面已通过。

### 3. 服务端没有定位时效与先后顺序校验

正式HTTP诊断实际复现：

| 用例 | 期望 | 当前结果 |
| --- | --- | --- |
| 上传一小时前采集的点 | 拒绝陈旧点，并保留当前点 | 返回200，覆盖当前定位 |
| 上传采集时间超前十分钟的点 | 拒绝明显异常时间 | 返回200 |

`server/rules.mjs` 的location分支只检查坐标范围、非负精度及 `capturedAt` 是有限数值。离线判断使用本次服务端接收时间，因此陈旧点被重新上传后还能显示在线。需要定义可容忍的设备时钟偏差、样本最大年龄及同队样本顺序，然后拒绝不合规样本。这里是新增异常验收标准暴露的缺口，不是既有36项回归发生退化。

### 4. 随机事件、通用通信及特殊人物挑战缺完整链路

- `event_create`：400 `COMMAND_UNKNOWN`。
- `send_message`：400 `COMMAND_UNKNOWN`。能力卡完成说明和任务审核回执已有实现，不能代表通用玩家/工作人员聊天已实现。
- `send_challenge`：400 `COMMAND_UNKNOWN`。最低分识别的沙箱检查可用，但“特殊人物收到目标定位→下发挑战→玩家接收→证据审核→结算”尚未形成完整正式流程。活动文案的“任务进度最慢”也不能直接等同于“当前积分最低”，需明确实际选队规则和定位权限。
- 正式新赛局清空 `eventTemplates`，区域到达虽产生待发事件，但抽取返回409 `EVENT_NOT_CONFIGURED`；沙箱里的测试+2事件不能算作正式事件池。正式页面也没有完整事件创作/抽取/发放控制。

需要补正式事件池、创作/发放/收件/确认接口，以及特殊挑战的目标选取、权限、接收、审核和结算；再以正式账号跨设备验收。

### 5. 切音游、锁屏后的定位与通知能力需要明确

现在只支持前台上报。切到音游、锁屏或让浏览器进入后台后，不会继续稳定上传；超过20秒没有更新，工作人员会看到离线。系统Web Push也尚未实现，消息存在数据库并不代表锁屏通知已送达。

活动打歌本身需要切换应用。需要先确定队长是否用另一台保持前台的设备持续定位，还是要求实现后台定位能力；不能把网页在前台的GPS通过当作打歌期间持续追踪已通过。

## 通信稳定性与展示仍需验证

- 断网/超时后的人工重试：服务端有幂等保护，但 `GameClient.request` 每次调用生成新键。首次请求已入库、响应丢失后再次提交，可能成为两份队列/媒体记录。需要同一操作沿用幂等键或增加业务去重。任务基础分的唯一归属已有保护。
- 当前正式页面用轮询同步，尚无正式赛局WebSocket路由和重连补取机制。若两秒轮询满足活动要求，可继续使用，但需要测延迟、401重新登录及断网恢复。
- 原图/视频仍存整场状态的数据库字段，GPS写入和 `/state` 读取更新都经过同一赛局行锁并重写JSONB。素材增多时可能影响定位、上传和审核延迟；这是待生产压测的结构性风险，不是本轮已复现的超时。需要使用代表性媒体数量/大小压测，再决定分离媒体、定位和状态存储。
- 正式定位界面当前展示坐标、在线状态及外部地图链接，没有完整的实时地图轨迹展示。后端历史点可读取不等于工作人员已能在界面查看路线。
- 安卓/iPhone文件格式、短视频播放与8MB限制尚未真机验证。当前只接受PNG/JPEG/WebP和MP4/WebM，HEIC/MOV不在接收范围；不能假定所有手机素材都能直接提交。

## 安卓与iPhone的实机验收步骤

在公网API恢复后，用独立验收赛局；两台手机分别登录不同队伍队长账号，另用工作人员设备登录具备定位权限的 `hrg-staff-01`。手机使用HTTPS入口，电脑局域网HTTP地址不满足当前安全上下文与后端地址校验。

1. 分别允许、拒绝定位，检查提示和手动恢复；拒绝定位不应阻断任务证据流程。
2. 每台手机在前台移动，工作人员核对坐标、精度、服务端接收时间和在线状态；持续至少70秒确认历史采样。
3. 原地静止至少一分钟，检查是否错误离线；不是只测移动时回调。
4. 切到音游/锁屏30秒，确认是否按当前规则停止更新并标离线；回到浏览器后确认无需刷新即可恢复。
5. Wi-Fi与蜂窝切换、断网30秒后重连，检查状态恢复、证据重试及重复记录。
6. 工作人员暂停/继续比赛，检查GPS监听、上传与界面反馈。
7. 手机提交实际照片、短视频，工作人员读取原件、审核，玩家读回回执及积分；验证另一队与普通工作人员的位置隔离。
8. 按区域顺序推进后确认一队完赛，检查该队停止采集和发送，另一队仍能持续更新。
9. 如要求锁屏接收通知，分别实测安卓浏览器/PWA和iPhone浏览器/PWA；当前Web Push未实现，不能提前标通过。
10. 另在隔离的远端数据库环境演练API异常退出和恢复，核对最后位置离线、积分/审核记录保留；本轮只证明本机持久化恢复。


定位诊断目前预期13通过、3失败，并返回非零退出码。缺口修复后重新运行，不能删掉失败用例来让结果变绿。测试使用正式HTTP路由、随机合成账号和独立数据库，结束时校验清理路径并删除临时数据库，不影响真实比赛。

优先顺序：公网API → 正式定位生命周期和样本时效 → 事件/通用消息/特殊挑战 → 双手机实测 → 远端恢复、媒体与并发压测。若活动必须支持锁屏定位或通知，这两项也应作为开赛前置条件。
